# V2.0.3 ID-PRIMARY MULTI-ID

## HeyID 页面以图片内 ID 为准

针对交友软件中数字/字母公共占位头像和高度重复页面模板：

- 一张图片可识别 **多个 HeyID**，不再只读取第一个。
- 图片内任意 HeyID 与历史库 HeyID 一致 → 直接判定撞客（匹配类型：`页面ID一致`）。
- 图片能可靠读取 HeyID，但与历史图片的 HeyID **全部不同** → 直接判定新客户；SSCD、pHash、模板、相同数字头像都不能覆盖这个结论。
- 例如 `FCN55877549` 与 `XBF55942411 / HLL50746941`：即使页面布局和渐变圆形头像高度相似，也不会撞客。
- 旧图库会后台建立“页面ID索引”，完成后任务自动停止；新客户入库时立即提取并保存 ID。
- `/aistatus` 同时显示页面ID扫描进度。
- 普通真人照片、生活照等没有 HeyID 的图片，仍使用 SSCD + Hash + SAFE-MATCH + 局部几何。

> V2.0.3 的 ID 规则优先级高于 V2.0.2 的模板/占位头像视觉规则。

# V2.0.2 PLACEHOLDER-GUARD + V2.0.1 TEMPLATE-ID-GUARD + V2.0 TEMPLATE-GUARD + V1.9.9 CLEAN-ENTRY-REPLY

## 本版新增：模板页防误撞

针对交友软件/社交软件中大量复用同一 UI 模板、同一渐变圆形头像框、同一白底版式的情况：

- 不再把公共页面模板当成客户照片特征。
- 当两张图都是资料页模板，并且都检测到可靠的大圆形头像区域时，额外比较**圆形头像内部的高频内容**。
- 同样的粉色渐变圆、同样的页面布局，但圆内是不同数字/汉字/不同头像时，会直接阻止“疑似撞客”。
- 完全同图 SHA256/MD5 仍然 100% 撞客。
- 同一头像经过 JPEG 压缩、缩放、左右镜像仍可正常通过同图识别。
- 这个 Guard 只负责**否决模板造成的假相似**，不会单独制造撞客。

# V1.9.9 CLEAN-ENTRY-REPLY + PRECHECKED-NEW DIRECT-ENTRY + AUTO-FIND-IMAGE + EDITED-CAPTION-ENTRY + REVIEW-FIX + MATCH-PREVIEW

## 实时客户入库规则

只要群里最终形成 **客户图片 + 正式客户资料**，且图片检测不是撞客，就自动正式入库。

支持以下发送方式：

- 图片和客户资料在同一条消息/caption。
- 先发图片，之后同一员工补发客户资料。
- 先发客户资料，之后同一员工补发图片。
- 客户资料直接回复之前的图片，优先按 message_id 精确绑定。
- A 发图片、B 回复该图片补资料，也可以精确绑定入库。
- 图片直接回复之前的客户资料，也可以绑定入库。

分开发送时图片和资料默认保留 1 小时。多人同时发客户时，明确的 Telegram 回复关系优先，未回复时只自动匹配同一发送者最近的记录，降低串客风险。

图片单独发送仍然只是查询，不会立即正式入库；只要在缓冲期内补齐客户资料，就会转为正式客户。

# TG 防撞客机器人 V1.9.1 SAFE-MATCH SSCD-AI COPY-GUARD

GitHub + Railway 群聊专用版本。私聊关闭。

## 识别目标

**一张照片 = 一个客户。** 系统判断的是“是否为同一张照片的编辑/截图/裁剪/压缩版本”，不是判断两张不同照片里的人是否为同一个人。

支持的主要变化：原图重存、Telegram 压缩、缩放、裁剪、放大、黑白边、圆形头像、轻微旋转、左右镜像、亮度/滤镜变化、头像出现在资料页截图中、部分模糊等。

## V1.9 AI

V1.9 新增 SSCD Copy Detection AI 作为主同图 AI，原来的 MobileNet 只在 SSCD 不可用时作为备用。SSCD 候选与 pHash/局部特征候选取并集，再用 SIFT/AKAZE/RANSAC 等做配对验证。

首次部署会下载约 99MB 的 SSCD TorchScript 模型到 `/data/models`；Railway Volume 挂载 `/data` 后只需下载一次。

## 判定规则

- 完全同文件：100%
- >=90% 且有强同图证据：自动撞客
- 85%~89.99%：疑似撞客；至少两类独立同图证据一致才会提示人工审核
- 明显不同：新客户

低信息图片会采用更保守的自动判定，避免不同纯色/简单默认头像因 pHash 相同而误撞。

## Railway 必须设置

Variables：

```text
BOT_TOKEN=你的机器人Token
DATA_DIR=/data
```

给 worker 挂载 Railway Volume：

```text
/data
```

V1.9 默认在 Railway 上强制检查 Volume。没有 Volume 时会拒绝启动，不会静默使用临时空数据库。

## AI 索引

升级后旧客户图片会在后台逐批生成 SSCD 描述符。群里发送：

```text
/aistatus
```

可以查看 AI 模型和历史图库索引进度。

BotFather -> `/setprivacy` -> 选择机器人 -> `Disable`，并建议把机器人设为正式群管理员。


## V1.9.2 MATCH-PREVIEW

- 撞客或疑似撞客时，机器人会把算法真正命中的历史图片直接回复到本次提交图片下面。
- 审核人员可直接上下对比“本次提交图”和“历史命中图”。
- 疑似撞客的【确认撞客 / 误判】按钮直接显示在历史命中图消息上。
- 如果历史图片文件不可读取，会保留文字结果并提示，不影响检测。
- 可通过 Railway 变量 `SHOW_MATCHED_IMAGE=0` 关闭历史图片展示；默认开启。


## V1.9.4 图片备注入库
Telegram 图片 caption/备注中包含正式客户资料时，图片与资料视为同一条正式客户记录并自动入库。支持多行和单行多字段。


## V1.9.5 REVIEW-FIX

- 修复历史命中图片上的【误判/确认撞客】按钮点击无反应。历史预览是媒体消息时改用 caption 编辑。
- 点【误判】后立即移除按钮、显示确认人，并把该图片/客户组合写入误判排除表，后续不再重复提示。
- 疑似区间新增独立证据门槛，降低树叶、木纹、围栏、UI/文字等重复结构造成的误判。
- SSCD AI 旧图库只有“待索引 > 0”时才每20秒补索引；达到100%后后台任务自动停止。
- 新客户正式入库时同步生成并保存 SSCD AI 特征，可立即参与下一张图片查撞。
- 旧图库补SSCD时使用完整多区域视图。
- 待人工审核图片在按钮处理前不会被孤立文件清理任务删除。

## V1.9.6 图片备注自动入库
- 支持图片发送后再编辑 caption 补客户资料（edited_message）。
- 图+资料一旦完整且不是撞客，自动正式入库。
- 疑似撞客若人工点“误判”，图片中已有的客户资料会自动入库。


## V1.9.7 自动找到原图片入库

- 客户资料直接回复旧图片：机器人从 Telegram `file_id` 自动重新读取原图片，重新查撞；不是撞客就直接入库，不要求补图。
- 常见流程“先发图片 → 再发『有人聊过吗』之类查询文字 → 后面回复这条查询文字补客户资料”也支持。机器人会把查询文字与前面的图片做持久化关联。
- 消息→图片关联保存在 `/data/customers.db`，Railway 重启/重新部署后仍可继续使用。
- 自动找到图片后会重新执行当前最新的同图/SSCD/SAFE-MATCH 检测；撞客不重复入库，疑似撞客仍走人工确认，确认误判后资料自动入库。
- 仅在同一员工最近图片 + 明显查询语句（例如“有人聊过吗/头像有人聊过吗”）时自动建立无回复关系的关联，降低多人群串图风险。



## V1.9.8 已查新客后资料直接入库

- 查询文字（如“有人聊过吗”）本身永远不入库。
- 图片第一次防撞为新客户后，会长期记录该图片为 `new`。
- 正式客户资料后来回复原图或回复与原图绑定的查询文字时，自动找到原图并直接入库，不要求再次补图。
- 已确认撞客不入库；疑似撞客仍需审核。误判后图片状态恢复为 `new`。
- 正式入库时即时生成 SSCD AI 特征。


## V1.9.9 入库回执精简

正式客户成功入库后，机器人只回复 `✅ 新客户已入库`，不再重复发送姓名、年龄、职业、引流软件、接粉人员等客户资料。客户资料仍完整保存到 `/data/customers.db`。


## V2.0.1 TEMPLATE-ID-GUARD

- 修复同一个交友软件公共模板、同一个数字/字母占位头像，但 HeyID 不同仍被误判的问题。
- HeyID / 页面账号ID只作为“排除误撞”的负证据，不会单独制造撞客。

## V2.0.2 PLACEHOLDER-GUARD

- 社交/交友软件的数字、单字母、单符号渐变圆头像视为公共占位头像，不再作为唯一客户图片证据。
- 两张公共占位头像页面只有在页面账号 ID（如 HeyID）被 OCR 可靠判断为同一 ID 时才允许继续进入相似图判断；ID 不同或任一侧无法可靠读取时，模板匹配直接被阻断。
- 相同 HeyID 也不会单独产生撞客，仍需 SSCD/Hash/局部几何等图片证据。
- 针对小字号 OCR 常见的 O/0、I/1、S/5、B/8 等误读加入保守容错，避免同一 ID 因一次 OCR 字符误读被错误阻断。
